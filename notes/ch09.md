### 9.1 - introduction to testing your code
- - -
- **scope creep** refers to when you add some new capabilities or expand your program that wasn't originally intended or planned for 
- **software testing/validation** is the process of determining whether the software actually works as expected
- test your programs in small pieces: whenever you plan on adding something to your code, test if it works by itself first and then retest it again after integrating it to your main code, this ensures that you catch issues and errors while they are still small and avoid ripple effects. testing a small part of your code in isolation is called **unit testing**
- some methods you can use to test your code in units are:
    1. **informal testing** - informal testing is when you add a unit of code, and to test it you write some code and after you finish testing the unit, you erase the code used to test it and then move on
    2. **preserving your tests** - although temporarily testing your code using informal testing is easy, it is tedious if you want to test the code again later (assuming you've added some new capabilities), you have to rewrite all the testing code again, to avoid this you can move the testing code into a test function which you can reuse to test your code multiple times at any given point
    3. **automating your test functions** -  one problem with a plain test function is that you still have to manually check the results yourself when you run it, so instead you can write the test function to also contain the expected answers and compare them internally, this way it tells you directly whether something passed or which specific check failed, so you don't have to remember or manually verify anything yourself
- once you have finished testing each unit of your code in isolation you can integrate it to the main codebase and then retest to check if they were integrated properly, this is called **integration testing**

### 9.2 - code coverage
- - -
- **code coverage** is used to describe how much of the source code of a program is executed while testing
- **statement coverage** refers to the percentage of statements in your code that have been tested by your testing routines
- **branch coverage** refers to the percentage of branches that have been executed while testing, for example: an if statement usually has 2 branches - one that executes when the condition is `true` and one that executes when the condition is `false` (of course, this can have many branches and a switch statement also has many branches)
- **loop coverage** (also called the 0, 1, 2 test) says that if you have a loop in your code, ensure that it works properly when it iterates 0 times, 1 time and 2 times, if it works correctly for the 2nd iteration it should work correctly for all the iterations greater than 2
- it is also good practice to test different categories of inputs (if your code takes in user input, or is passing some arguments to another function) to ensure that the unit handles them properly (for example: when using integer inputs you can test positive, negative and zero values, when taking string input you can test it with alphanumeric input, whitespaces etc.)

### 9.3 - common semantic errors in cpp
- - -
- one of the most common types of semantic errors is a **conditional logic error**, a conditional logic error occurs when the programmer incorrectly codes the logic of a conditional statement or a loop condition, this can cause undefined behaviour and might produce results that were not intended
- **infinite loops** are also very common and we've read about it in the previous chapter, this might occur when the programmer forgets to update the loop variable and the loop just keeps running indefinitely causing undefined behaviour
- **off-by-one** errors are also a major cause, we've already covered it in the previous chapter and it happens when you iterate through a loop one too many or one too few times
- **incorrect operator precedence** can also produce unexpected results, to avoid this ensure you explicitly parenthesize your expressions properly 
- issues with **floating point precision** can also produce results that weren't intended when tested against the equality or inequality operators
- **integer division** works in a different way compared to floating point division so it can also be a cause of error
- **accidental null statements** lead to undefined control flow or infinite loops depending on the condition, most probably cause is when you end an if statement or loop with a semicolon `;` so it treats the body as if it was a null statement
- **not using compound statements**, in simple terms when you don't properly put your statements inside a block when required, it causes unintended flow of control 
- **using = (assignment) instead of == (equality)** is also one of the most common causes of errors, most programmers tend to miss this completely sometimes
- these are just some of the common errors made by programmers, however semantic errors might be of any type depending on your code

### 9.4 - detecting and handling errors
- - -
- most bugs aren't from misusing language features, they're from assumptions the programmer made that turned out false
- three common spots assumptions sneak in: a called function might've failed, input might not be in the right format, arguments passed into a function might not actually be valid
- happy path = testing only when everything goes right, sad path = testing the ways things can actually go wrong, you need to plan for both
- four ways to handle an error once found: handle it inside the function, pass it back to the caller, halt the program, or throw an exception
- handling it internally means either retrying until it works, or just cancelling/skipping the operation, silently skipping is bad since the caller has no clue something failed, so printing an error message is better
- passing errors back to the caller: if the function returns void, just change it to return bool instead (true/false for success/failure)
- if the function already returns a real value, use a sentinel value instead, a value that could never legitimately occur, to signal failure, only works if such a value actually exists for that function
- fatal/non-recoverable errors mean the program just can't continue properly, best fix is to return a non-zero value from main, or use std::exit() if you're too deep in nested functions to propagate the error back up
- exceptions are a separate way to pass errors up automatically through the call chain without every function manually checking and forwarding a return code, actual details come way later (ch 27)
- std::cout is for normal user-facing messages, std::cerr is for technical/diagnostic stuff not meant for regular users, a logfile is for programs that need a permanent, reviewable record of ongoing events
