# ch7 - scope, duration and linkage

### 7.1 - compound statements (blocks)
- - -
- a **compound** statement (also called a **block**) is a group of zero or more statements that are treated by the compiler as if it were a single statement
- blocks begin with a `{` and end with `}`
- functions can't be nested inside other functions, but blocks can be nested inside other blocks where the enclosing block is called the **outer block** and the enclosed block is called **inner/nested block**
- the **nesting level** of a function is the maximum number of nested blocks you can be inside at any point in the function, the maximum number of levels supported for now is 256

### 7.2 - user defined namespaces and the scope resolution operator
- - -
- cpp allows us to define our own namespace, namespaces that you create in your own programs are called **user-defined/program-defined** namespaces
- the namespace must be defined in the global scope, or inside of another namespace
- the best way to tell the compiler to look inside a particular namespace for an identifier is to use the **scope resolution operator** (`::`)
- when you use the scope resolution operator in front of an identifier without providing a namespace name, it will look for the identifier in the global namespace, this is useful when you are inside of a namespace and explicitly want to call a function from the global namespace
- when using namespaces with header, the forward declarations also need to be in the same namespace 
- it is legal to declare namespace blocks in multiple locations, all declarations within the namespace are considered part of the namespace
- namespaces can be nested, meaning you can declare a namespace within another namespace
- you can use namespace aliases to temporarily shorten the name of a namespace, for testing purposes

### 7.3 - local variables 
- - -
- local variables have block scope, meaning they are in scope from their point of definition till the end of the block in which they are defined
- a variable's **storage duration** determines what rules govern and when and how a variable will be created and destroyed, in most cases this duration directly determines a variable's lifetime
- local variables have automatic storage duration, meaning they are created at the point of definition and are destroyed at the end of the block, which is why they are also called automatic variables sometimes
- nested blocks are considered to be a part of the scope of the outer block in which they are defined, so for this reason the variables defined in the outer block can be seen inside a nested block
- identifiers have a property known as **linkage**, an identifier's linkage determines whether a declaration of that same identifier in a different scope refers to the same object
- scope determines where an identifier can be seen and used, linkage determines whether multiple declarations of the same identifier refer to the same object or not

### 7.4 - introduction to global variables
- - -
- you can also declare variables outside of a function, such variables are known as **global variables**
- global variables are usually declared at the top of the program file, below the header inclusions, in the global namespace
- these variables have a **global namespace scope** (also called global scope or file scope), which means they are visible from the point of declaration until the end of the file in which they are declared
- global variables can also be defined inside a user-defined namespace, it makes the identifier of the global variable limited to the scope of the namespace but, the name and variable itself are still globally accessible (read the example in 7.4 if you didn't understand), it is usually recommended to define global variables inside a user-defined namespace instead of just the global namespace
- these variables are created when the program starts and they're destroyed when it ends, this is called **static duration**, variables with a static duration are sometimes referred to as **static variables**
- to differentiate global variables from local ones, you use the prefix 'g_' or just 'g', however you can omit it if you are defining it inside of a user-defined namespace since it serves the same purpose
- global variables are zero-initialized by default, unlike local ones which are uninitialized

### 7.5 - variable shadowing (name hiding)
- - -
- when we have a variable that is nested inside a block, with the same name as a variable from the outer block, the nested variables temporarily hides the outer variable in areas where they are both in scope, this is called **name hiding** or **shadowing**
- when inside a nested block, there is no way you can directly access the shadowed variable from the outer block
- similar to how the nested variable shadows the variable from the outer block, a local variable also shadows a global variable with the same name in areas where they are both in scope, however since global variables are part of the global namespace, we can use the scope operator (`::`) with no prefix to tell the compiler we want to access the global variable

### 7.6 - internal linkage
- - -
- if you forgot what linkage is: it just answers one question: "if i use this name in different places, does it refer to the same thing or different things?"
- there are three types of linkage: no linkage, internal linkage and external linkage
- a variable/function with **internal linkage** is only visible/usable inside the one file it's defined in, your other files have no idea it even exists
- global variables with internal linkage are sometimes referred to as internal variables
- to make a non-constant global variable internal, you have to use the `static` keyword, otherwise it defaults to external linkage
- const and constexpr global variables have internal linkage by default and don't need the `static` keyword
- functions also default to external linkage and can be set to internal linkage with the `static` keyword
- note that identifiers with internal linkage aren't exposed to the linker, i.e internal linkage limits the use of an identifier to a single file

### 7.7 - external linkage and variable forward declarations
- - -
- an identifier with **external linkage** can be seen and used both from the file in which it is defined and also other code files using forward declaration
- identifiers with external linkage are visible to the linker, so this allows the linker to connect an identifier from one translation unit with the definition of said identifier in another translation unit
- global variables with external linkage are sometimes referred to as **external variables**, to make a global variable external, we use the `extern` keyword, and since non-const global variables are external by default we don't need to use the `extern` keyword for them
- to use a global variable from another file, you must place a forward declaration for said global variable, this is done using the `extern` keyword too, even for non-const global variables
- the keyword `extern` has different meanings in diffrent contexts, it can mean "give this variable external linkage" or even "this is a forward declaration for an external variable used somewhere else"
- note that if you want to define an uninitialized non-const global variable, do not us the `extern` keyword, cpp will think you're trying to make a forward declaration
- also constexpr variables can be given external linkage using `extern`, they cannot be forward declared as constexpr
- function forward declarations do not need the `extern` keyword, the compiler is able to tell whether the statement is a new function definition or a forward declaration based on the presence of a function body


### 7.8 - why (non-const) global variables are evil
- - -
- refer to learncpp to see why using non constant global variables is discouraged, especially in larger systems, too big to put it here 
- although there is still something to note here, the initialization of static variables happens as part of program startup before execution of the main function 
- the first phase is called static initialization:
    1. global variables with constexpr initializers are initialized to their respective values, this is called constant initialization 
    2. global variables without an initializer are initialized with zero by default, this is also considered to be a form of static initialization since `0` is a constexpr value
- the second phase is called dynamic initialization, here the global variables with non-constexpr initializers are initialized
- if you look at the source file, ch7-08 you can see that g_x is initialized first (since it's declared first), and its initializer function tries to read g_y. but g_y hasn't been dynamically initialized yet at that point, it's still sitting at its phase-1 default value, 0. so g_x ends up 0 instead of 5, and only afterward does g_y actually get set to 5. that's why the output is 0 5, not 5 5
- so in general, you should avoid initializing static objects with other static objects from different translation units
- as a rule of thumb, any use of a global variable must at least meet two of the following criteria:
  1. there should only ever be one of the thing the variable represents in your program 
  2. its use should be ubiquitous (same everywhere) throughout the program

### 7.9 - inline functions and variables 
- - -
- if you take a function, lets say a minimum of two numbers, called `min()` which takes in two parameters - `x` and `y`, when you call the function the CPU must store the address of the statement calling the function so that it knows where to return back later, then the arguments for parameters `x` and `y` are instantiated and initialized, then the execution jumps to the function, and after processing the return value is sent back to the caller and then it jumps back to where it was and executes the rest. this happens for each function call
- all of this extra work that must happen in order to setup, facilitate or cleanup after some task is called **overhead**
- **inline expansion** is a process where a function call is replaced by the code from the called function's definition
- although this improves performance by optimizing the code, it has its own costs, for example if the body of the function being expanded takes more instructions than the function call being replaced, then each inline expansion will cause the executable file to grow larger and larger executables tend to be slower
- so it is just suited for short and simple functions (no more than a few statements)
- a function being declared using the **inline** keyword is called an **inline function**
- in modern cpp, the term 'inline' has evolved to mean "multiple definitions are allowed", so an inline function is one that is allowed to be defined in multiple translation units
- so as a performance tool, inline doen't really do anything anymore and its just dead weight being kept for historical compatibility
- what inline does today is completely different - it tells the linker "if you find multiple definitions of this specific function across different files, that's expected and it's not a mistake, they're just copies of the same header included code, treat them as one and discard the extras instead of throwing an error"
- surprisingly, there's actually a real historical connection as to why the inline function serves a completely different purpose today, back then to inline-expand a function call, the compiler had to be able to see the function's full body at compile time, meaning if you wanted a function to be inlined everywhere it was alled, the full body had to be visible in every file that called it, so it had to live in a header included everywhere, but that creates a problem: multiple definitions aren't allowed. so the rule became: mark it inline and it's excused from the multiple definition error
- so originally "please inline this" and "you're excused from the odr were bundled together because you needed the second thing to make the first thing possible at all, today's compilers do inlining on their own regardless of the keyword so the only meaningful thing you get from writing inline as a keyword is the linker exemption
- there are three rules for a valid inline function:
  1. the full body must be visible in every file that uses it (not just declaration)
  2. only one definition alowed per file (i know this seems contradictory but i'll explain in the next point)
  3. every copy across all the files must be identical, if they're not, the compiler won't catch it but it will cause undefined behaviour
- the odr required for the rule and the odr that inline is bypassing are both completely different, one is at compile time and the other is a linker exemption, the rule refers to the individual file itself which requires no duplicate of a function as the compiler will throw an error and it doesn't make sense syntactically, but when same function is used in defined in other files, this is allowed as it is a linker exemption from inline (that's the entire purpose)

### 7.10 - sharing global constants across multiple files (using inline variables)
- - -
- a quick recap on what linkage means: it controls whether a name is visible only inside the one file its compiled in or visible to the linker so other files can reference the same thing, internal linkage = limited to that one file and external linkage = visible across all files and the linker can be used to connect them 
- by default, `const/constexpr` globals have internal linkage, so when you use a library like `#include "constants.h"` let's say, the compiler copy pastes the namespace (if used in header file) and the variables directly into main.cpp's text, now because the constant being used has internal linkage, its copy belongs entirely to main.cpp so even if another file includes the same constant, the linker never sees it so there is no odr violation 
- note: constexpr functions are implicitly inline, but constexpr variables are not, to inline a constexpr variable you have to explicitly mark it as inline 
- for the situation stated above (i.e for example say use of constant values across multiple translation units), there are different methods to approach it 
  1. for the first method - you can use a header file and put all the constant values in it, inside a namespace and include the header file wherever needed, but the downside to this is that it creates too many duplicates, and needs recompiling everytime there is a change in a constant value or a new value gets added or removed
  2. for the second method - you can put all these constant variables inside a seperate .cpp file and use them as external variables, put the forward declarations for this in a header and include the header wherever needed, the downside to this is that these values cannot be used in constexpr statements as the value of the variable needs to be known at compile time and forward declaring the variables isn't doing so, and since they can't be constexpr, there isn't much room for optimization either
  3. for the third method - you can declare all these variables in a header file using the inline keyword, which deals with the duplication issue from the first method, but still the re-compile issue remains, this is recommended in general 

### 7.11 - static local variables
- - -
- using the static keyword on a local variable changes its duration from automatic to static, this means that the variable is now created at the start of the program and destroyed at the end of it, as a result: the static variable will retain its value even after it goes out of scope
- static variables that are zero-initialized or have a constexpr initializer can be initialized at the start of the program and the ones with no initializer or non-constexpr initializer are zero initialized at the start of the program
- the static variables with a non-constexpr initializer are reinitialized the first time the variable definition is encountered
- so essentially, static variables are used when you need a local variable to remember its value across multiple function calls
- you might be asking the question, "why not just use global variables?" it's because a global variable is visible and modifiable from any function in the file, but a static local variable is only visible and modifiable inside the one function its declared in, while still keeping its value throughout multiple calls
- a static local variable has a block scope, just like a local variable but its lifetime remains until the end of the program
- they're also used to avoid expensive local initialization every time the function is called
